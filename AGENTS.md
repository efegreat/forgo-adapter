# AGENTS.md

Guide for coding agents and contributors working **on forgo-adapter itself**. For how to *use* the adapters, see [REFERENCE.md](REFERENCE.md). [README.md](README.md) is the public entry point.

## What forgo-adapter is

The concrete infrastructure for [forgo](https://github.com/efegreat/forgo): resources (SQL, Redis, RabbitMQ, Google Cloud Pub/Sub, Redis Streams) and providers (a SQL transactor, inbox/outbox storages, live config stores and a live config cache, a Redis locker, a Redis rate limiter) that implement forgo's interfaces, and the OpenTelemetry metrics of forgo applications. Each client library is a module of its own (see [Modules](#modules)): the root module, `github.com/efegreat/forgo-adapter` ([repository](https://github.com/efegreat/forgo-adapter)), holds the SQL adapters, and `github.com/efegreat/forgo-adapter/redis`, `…/rabbitmq`, `…/pubsub` and `…/otel` the others. Go 1.27. Every `go.mod` requires a released forgo, and never replaces it: modules that depend on this one ignore its `replace` directives, so a module that replaces forgo does not build for them, and the release job of CI refuses its tag. To work on a change of both repositories, use an uncommitted `go.work` (`go work init . ./redis ./rabbitmq ./pubsub ./otel ../forgo` at the root, which `.gitignore` keeps out), and once the forgo change is on its `main`, require that commit (`go get github.com/efegreat/forgo@<commit>`) until forgo releases it.

The dependency points one way. **Adapters import forgo; forgo never imports adapters.** Anything a server needs from an adapter is an interface declared in forgo. When a forgo contract changes (`worker.IBroker`, `worker.InboxStorage`, `operation.ILocker`, `ratelimit.ILimiter`, `forgo.LiveConfigStore`, `forgo.LiveConfigCache`, `operation.IObserver` and its extension interfaces, …), update the adapters here in the same change set.

forgo's [AGENTS.md](https://github.com/efegreat/forgo/blob/main/AGENTS.md) applies here too: its design principles, coding conventions and logging rules. This file only adds what is specific to adapters.

## Design principles

forgo's four goals carry over:

1. **Simplicity.** A resource is a config value, a provider is a constructor. Zero fields mean defaults, filled by `Sanitize()`. Optional features, such as `rabbitmq.DeadLetterConfig`, are config structs whose zero value turns them off.
2. **Speed.** Connections, topology and scripts are set up in `New` and in constructors. Hot paths, such as `Allow`, `Lock` or `Publish`, do one round trip and no reflection, and Redis scripts are sent with `EVALSHA`.
3. **Abstraction.** An adapter implements a forgo contract and nothing more. It does not log, and it reports through returned errors. Logging, retries and acknowledgement policy belong to the forgo servers. The one exception is `sqldb`'s opt-in query log, which observes the application's own statements rather than the adapter's decisions.
4. **Scalability.** Shared-state adapters must be correct with many app instances: atomic Redis scripts, `FOR UPDATE SKIP LOCKED` claims, the Redis server clock.

## Invariants

Do not break these without an explicit decision from the maintainer.

### Resources

- `Config` is a value type with value receivers. `Sanitize()` returns a copy with defaults. It **never writes into the caller's slices or maps**, because configs are package-level vars shared by several apps and tests. Build new slices, and clone maps before adding keys (see `QueueConfig.args`). The same holds for what `New` hands to a client: the go-redis cluster client appends discovered nodes to its seed list, so `redisdb` clones `Addrs`, and amqp091-go writes `ServerName` into its TLS config, so `rabbitmq` clones `TLSConfig`.
- `New()` follows this order: `Sanitize` → `validate` (no network) → connect → verify (ping, declare). On any failure after connecting, close what was opened and join the close error with `errors.Join`.
- `Value()` returns the concrete client (`*sql.DB`, the `*redis.Client` or `*redis.ClusterClient` of `redis.NewUniversalClient`) or, for brokers, the forgo interface (`worker.IBroker(r)`). Bootstrap binds the dynamic type of `Value()` and matches by assignability. Document in REFERENCE.md what providers should request.
- `Close()` releases everything `New` opened.
- The resource types (`sqldb`'s and `redisdb`'s `resource`, the brokers' `broker`) and the brokers' `publisher`, `subscriber` and `delivery` are unexported. `New` returns a `forgo.Resource` and the brokers return forgo's interfaces, so nobody needs to name them, and v1 does not freeze them.

### Providers

- One exported constructor per implementation, `NewX(dep) *X`, listed directly in `forgo.WithProviders`. Return the concrete pointer. Bootstrap matches it to the forgo interface by assignability, and returning an interface would hide the type from other providers.
- Ask for the narrowest dependency that works with every deployment shape: `*sql.DB` for SQL and `redis.UniversalClient` for Redis, so cluster and failover clients plug in.
- Every implementation has a compile-time assertion in its tests: `var _ operation.ILocker = (*Redis)(nil)`.

### RabbitMQ

- Published messages carry `worker.MessageIDHeader`, `MessageNameHeader` and `MessageTimestampHeader`, written from the `Message` fields over any user header of the same name. The consumer inbox depends on a stable ID across redeliveries.
- `newDelivery` keeps every header. `headerValue` converts values that are not strings to text, and tables and arrays to JSON, because `Message.Headers` holds strings only. Retry copies are built from the raw `amqp.Delivery` headers, never from `Message.Headers`, so they keep the AMQP types.
- `Delivery`: `Complete` = ack, `Retry` = nack with requeue, `Reject` = reject without requeue. When the queue has `Retry`, `Retry` instead publishes a confirmed copy to the retry queue for its attempt and then acks through the `ackGuard`. When it has `DeadLetter`, `Reject` publishes a confirmed copy to its dead-letter exchange and then acks, because RabbitMQ's own dead-lettering is at most once and the inbox already marked the message. Both check staleness before publishing, so a stale delivery is not duplicated, and fall back to nack with requeue when the publish fails, so the message is never held or lost: forgo's idempotency guard rejects the redelivery of a *failed* or *rejected* message again. A failed dead-letter copy first parks the delivery in the queue's last retry queue, when it has `Retry`: a requeued delivery comes back at once, ahead of the queue's other messages, and a dead-letter queue that keeps refusing copies would otherwise take every handler. Both copies go through the subscriber's `copier` (`newCopies`), behind the `confirmedPublisher` interface for tests.
- The broker has two connections, and every channel lives on the one of its kind: subscriber and topology channels on `conn`, publisher channels, the subscribers' copies included, on `publishConn`. RabbitMQ blocks a connection that publishes during a memory or disk alarm, and every channel on it, so a channel that publishes on `conn` would stall the subscribers until the alarm ends. Each connection has its own `recoveryHooks`: `loseConnection` closes the gates only for the publishing connection, and marks deliveries stale and gives up subscriptions only for the other one. A loss of one connection must never touch the other's channels.
- The client checks a publish's context only before writing, and blocks in the write once the socket's buffer is full. `flow` follows the broker's `connection.blocked` notices on `publishConn`, and `publish` waits, within its context, while it is blocked, instead of writing. A lost connection unblocks it, since the broker blocks the next one anew.
- The copier waits for recovery (`waitsForRecovery`): while the publishing connection is down, a copy waits for it within the acknowledgement's context instead of failing at once, because a failed copy requeues its delivery at once and its handler would run again and again. The client closes a lost channel before it runs the hooks, so a copy can also find its channel closed while the gate is still open: it then waits for the hooks to close the gate (`gate.waitLoss`). The outbox's publishers fail fast instead, so the relay moves on. Without recovery, the copier fails fast too.
- `Close` bounds every close handshake by `closeTimeout` and ignores `amqp.ErrClosed` and socket errors: a connection that is down or a broker that does not answer must not make a SIGTERM during an outage fail the app, and a channel close that waits for the broker would hold the consumer server's `Terminate`.
- `declare` declares a queue's retry queues **after** the queue. They are durable, and dead-letter through the default exchange (`x-dead-letter-exchange: ""`) with the queue's name as routing key, so an expired retry returns to that queue only. Their names derive from the delays, so changing `Retry` declares new ones and never redeclares an existing queue with other arguments.
- `declare` declares a queue's dead-letter exchange and queue **before** the queue. Dead-letter exchanges are durable direct exchanges and dead-letter queues are durable. Conflicts between `DeadLetter` and `x-dead-letter-*` in `Args` are rejected in `validate`.
- `Consume` waits for every handler it started (`handlers.Wait`) before returning. It returns `nil` when `ctx` ends and an error when the delivery channel closes without a recovery replacing it.
- A stream that ends while its channel is open, without a recovery replacing it, was ended by the broker: it cancels the consumer of a deleted queue, and from RabbitMQ 4.3 on, that of a quorum queue whose delivery outlived the consumer timeout. `next` then cancels the consumer itself and subscribes again (`consumeAgain`) under a new tag, with the same guard generation, because delivery tags go on and the cancelled consumer's other deliveries are still settled on the channel. A quorum queue keeps a consumer that timed out (activity status `timeout`), with its tag in use (consuming under it closes the channel with `NOT_ALLOWED`), and can deliver to it again once its late delivery is acknowledged, into the stream the client dropped: those deliveries waited unacknowledged until the broker timed them out and closed the channel with `PRECONDITION_FAILED`, which delivered them again one consumer timeout late. The cancellation removes it, which `TestIntegrationConsumerTimeout` checks by consuming under the old tag. The broker acknowledges the cancellation of a consumer it no longer has, such as that of a deleted queue. A subscription that cannot cancel or subscribe again is lost.
- Recovery is the client's (amqp091-go `Config.Recovery`), wrapped by `recoveryHooks`, which is both the `ConnectionRecovery` and the `TopologyRecovery`. The hooks recover only channels in `Broker.owned`. The close hooks run before the client reopens a channel, the client's recovery runs inside them, and `RecoverTopology` runs once the channels are open again.
- The close hooks advance the `ackGuard` of a subscriber channel before the client reopens it, and the guard's read lock spans every acknowledgement. Never acknowledge a delivery around the guard: delivery tags restart on a recovered channel, so a stale tag settles another message. A channel's hook advances it only while the channel is closed, because it can run late, once its connection's recovery reopened the channel and subscribed again. The connection's hook does nothing while the connection is open: the client hands it the close of every reconnection attempt that failed once it dialed, after the attempt that reconnected, and nothing would subscribe again on the deliveries it marked stale.
- Never send on a channel the client is reopening: it resets the channel before it puts it back in confirm mode, and a message published in between is never confirmed and shifts every later confirm by one, for good. The close hooks close the publisher channel's `gate` around the client's recovery, and `publish` sends under the gate's read lock. A confirm that the loss nacked fails with `errChannelLost` and the loss's reason.
- The client would resume a consumer on its old delivery channel, after the deliveries of the lost channel that it still buffers, whose tags would reach the reopened channel. So `RecoverTopology` cancels the client's consumer of each subscriber (`detach`), which ends the old stream after what it buffers, lets the client recover the exchanges, queues and bindings, declares the configured auto-delete queues again (the client forgets them once no consumer of its own is left), and subscribes again on a new stream (`resubscribe`). Each `stream` carries the guard generation of its channel incarnation, and `Consume` drops the deliveries of a stream whose generation is stale and moves to the next stream when one ends. A subscriber that cannot subscribe again, or whose recovery gave up after `detach`, is reported to its `consumerLoss`, and `Consume` returns `errConsumerLost`. A lost subscription is never subscribed again.
- `RecoverTopology` skips every exchange, queue or binding that fails to recover, as the client does by default, so one failure never stalls the whole connection in reconnect attempts. Each subscriber consumes under a tag of its own (`forgo-<name>-<n>`, unique on the connection), never the client's generated one.
- The topology channel stays open for the broker's lifetime, because the client forgets the topology recorded on a closed channel.
- `NewSubscriber` checks the queue with a passive declare **before** the channel is owned, so the channel the broker closes on a missing queue is not recovered. It receives the worker's concurrency (`worker.SubscriberOptions`), which sizes the default prefetch and the copier. Prefetch (`basic.qos`) must precede `basic.consume`, and `Consume` sets both, since a subscriber delivers only while `Consume` runs: the worker waits for the handlers by waiting for it.
- Publisher channels are in confirm mode. `Publish` holds the publisher's mutex from publish to confirm, so one message is in flight per channel and a mandatory return can be matched to it by message ID. The outbox's relay publishes in parallel through a publisher per slot.
- A subscriber's copies are not one in flight per channel: its handlers copy at once, and waited in line for one confirm after the other, each holding its slot (with 5 ms of latency, 32 handlers retried 136 messages a second one confirm at a time, and 2,500 with their copies in flight together). The `copier` serializes only the sends, which the client documents as unsafe at once on a channel, and awaits as many confirms at once as the subscriber has handlers. A copy claims its return by message ID, exchange and routing key, among the returns it takes from the listener once confirmed, and frees its room in flight only after that, also when it stopped waiting for the confirm (it then claims in the background). The client stalls the whole connection while a return listener is full, and a broker can return every copy in flight before it confirms one, so the copier lets as many copies in flight as its listener has room for (`newCopier`), and `newCopies` gives the listener room for the copies of every handler. A handler copies one delivery at a time, so a copy waits for room only behind copies whose handlers stopped waiting for their confirms. A slot of the listener costs 264 bytes, far less than the handler's goroutine.
- Open and close channels only while the app starts and stops (`New`, `NewPublisher`, `NewSubscriber`, `Close`), never while it runs. amqp091-go v1.15.0 keeps a channel closed while its connection is down in the connection's registry, marked as closed by the application, and every reconnection attempt then fails on it with `504`: the connection never recovers. This is why the copier copies on one channel instead of opening more for a burst, which `TestIntegrationCopierRecovery` caught. The client also reopens the channels of a connection one after the other, two round trips each, while every publish on the connection waits.

### Pub/Sub

- Published messages carry `worker.MessageIDHeader`, `MessageNameHeader` and `MessageTimestampHeader` as attributes, written from the `Message` fields over any header of the same name. `Message.Destination` is the topic and is required, `Message.Key` is the ordering key.
- Every `Publisher` of a broker shares one client publisher per topic (`topics`), so the worker's parallel publishes are batched, and the broker stops them in `Close` before it closes the client. `topics.stop` waits for them for at most `stopWait`: by then the worker's publishers are done, so a pending message is one whose `Publish` gave up waiting, which the client retries for a minute and the outbox publishes again, and closing the client ends those retries. They have `EnableMessageOrdering` on, so a `Key` never fails a publish. After a failed publish, `topics.publish` resumes the message's ordering key, which the client paused: the outbox retries the message later.
- `Delivery`: `Complete` = ack, `Retry` = nack, both through their `*WithResult` variant and waiting on the result, which only takes time with exactly-once delivery. The retry delay is the subscription's retry policy, and the attempt is not used. `Reject` publishes a copy to the dead-letter topic, waits for it and acks, or only acks without a dead-letter topic. When the copy fails, it nacks: it never acks a message whose copy was not stored. forgo's idempotency guard rejects the redelivery of a *failed* or *rejected* message again, so the copy is retried until it is stored.
- Pub/Sub's dead-letter policy cannot be triggered by the client, which is why `Reject` publishes copies. `DeadLetterConfig.MaxDeliveryAttempts` only adds the policy as a backstop for messages that keep failing without a verdict.
- `Consume` sets `ReceiveSettings.MaxOutstandingMessages` before `Receive`, and bounds the handlers with a semaphore of the worker's concurrency, because `Receive` runs up to `MaxOutstandingMessages` callbacks at once. A callback that gets no slot before the context ends nacks its message. `Receive` returns only after every callback returned **and every message it delivered was settled**, so every path settles its delivery. The worker does that for the deliveries it handles. Its last acknowledgements are unary RPCs with a 60-second timeout each, so while Pub/Sub does not answer, `Receive` takes a minute to return. `receive` therefore runs it in a goroutine: once the context ended, it takes every slot, which waits for the running handlers and keeps later callbacks from starting one (they nack), then waits at most `flushWait` for `Receive`, which runs on until the broker's `Close` closes the client.
- `Consume` returns `errReceiveStopped` when `Receive` ends without an error before its context, so a subscriber never stops consuming silently.
- The client retries most stream errors itself, but `Receive` returns when a stream ends with `ResourceExhausted`, `Unknown` (other than a GOAWAY) or `Unavailable` "Server shutdownNow invoked". `Consume` calls `Receive` again after the codes `retryable` accepts, with a pause from `receiveRetryInitial` doubling to `receiveRetryMax`, reset after a `Receive` that lasted `receiveRetryMax`. Every other error, and any error once the context ended, returns. pstest cannot inject errors into `StreamingPull`, so the tests end streams through a gRPC client interceptor on the client's connection (`endingStreams`).
- `New` creates only the topics and subscriptions listed in the config, and never updates one. An existing subscription must equal the config in every setting `differences` compares; a dead-letter subscription only in its topic (`topicDifference`). Created subscriptions never expire.
- `NewSubscriber` does not check that the subscription exists: `roles/pubsub.subscriber` cannot read subscriptions. `Receive` fails at once on a missing one.
- `NewClient` receives `context.Background()`, never a context with a deadline: the client keeps it for its credentials.
- Live tests against the emulator (`gcloud beta emulators pubsub`) cover what pstest cannot, but run outages there without a retry policy: with one, the emulator never redelivers a message nacked while a stream broke, which the official client alone reproduces, and it applies the policy's backoff only roughly. Ordering, filters and exactly-once delivery work on it.

### Redis Streams

- Published entries carry `worker.MessageIDHeader`, `MessageNameHeader` and `MessageTimestampHeader` as fields, written from the `Message` fields over any header of the same name, plus `KeyField` and `PayloadField`. Headers named `KeyField` or `PayloadField` are dropped. `Message.Destination` is the stream and is required. An entry without `x-msg-id` takes the entry ID, which is stable across redeliveries.
- A group is a subscription: `declare` creates the listed groups with `MKSTREAM` and treats `BUSYGROUP` as success, never moving an existing group. Each subscriber reads as a consumer of its own (`consumerName`), created with `XGROUP CREATECONSUMER` in `NewSubscriber`, which also fails at startup on a missing stream or group.
- `Consume` reads (`XREADGROUP COUNT`) no more entries than it holds free slots, and claims before reading: `XPENDING … IDLE` finds the due entries in one round trip, however many wait for a retry (`XAUTOCLAIM` takes one per ten pending entries per free slot, and reads wait for a scan to end), and `XCLAIM` takes them, rechecking their idle time, with a cursor kept across passes. `XCLAIM` goes through `Do`, because Redis before 7.0 claims a pending entry trimmed from the stream and replies null for it, which fails go-redis's typed reply: `dropTrimmed` acknowledges the due entries the claim did not return that `XRANGE` no longer finds, as Redis 7 drops them itself, and leaves those another consumer claimed first. The read and claim commands run on `context.WithoutCancel`, so entries Redis handed over are always handled rather than left pending until `ClaimIdle`. `Consume` joins its handlers, then stops the heartbeat, in that order.
- Every in-flight entry is refreshed with `XCLAIM … JUSTID` every `ClaimIdle`/3, so handlers may outlive `ClaimIdle`. `inflight` is keyed by `*Delivery`, not entry ID, because a retried entry can be claimed again before the handler that retried it returns. Settlements remove their delivery from `inflight` **before** their command, and `remove` waits for a refresh in progress, so a refresh never reclaims an entry that was just parked or acknowledged.
- `Retry` never re-adds an entry, which would deliver it to every group of the stream. It parks the entry under the consumer `forgo-retry` with `XCLAIM … IDLE (ClaimIdle − delay) JUSTID`, so the claim of any consumer picks it up once due. Hence `Retry.Max ≤ ClaimIdle`. `forgo-retry` is never deleted.
- `Reject` adds the dead-letter copy, then acknowledges: two commands, because the dead-letter stream may hash to another cluster slot. A failed copy parks the entry for `longestDelay` and never acknowledges it, and forgo's idempotency guard rejects it again once claimed. Parked for an immediate claim, every scan would hand such entries to the handlers again while the dead-letter stream cannot be written.
- Out of memory with `noeviction`, Redis refuses `XGROUP CREATE` and `XGROUP CREATECONSUMER` (`OOM`) even when the group or consumer exists, while `XREADGROUP`, `XCLAIM`, `XACK`, `XPENDING` and `XINFO` still run (and, before 7.0, `XGROUP DELCONSUMER` and scripts that write fail too, so `Close` and the sweep fail and leave the consumer). `declare` and `NewSubscriber` therefore accept `OOM` when `XINFO GROUPS` finds the group: the first `XREADGROUP` creates the consumer.
- Consumers are deleted only through `delConsumerScript`, which checks `XPENDING` for that consumer first in the same script: `XGROUP DELCONSUMER` drops a consumer's pending entries from the group. `Close` deletes the subscriber's own consumer. `sweep` deletes the consumers of crashed instances: those without pending entries, idle for `staleIdle` × `ClaimIdle`, other than its own and `forgo-retry`. Before Redis 7.2, `idle` resets only when a consumer gets entries (since 7.2, on every read or claim), so on a quiet group it deletes live consumers too. That is harmless: they hold no pending entries, and Redis recreates them with their next entry. It runs from the claim loop once a scan reached the end, at most every `sweepInterval`, in one pipeline of `EVAL` (`Script.Run` falls back from `EVALSHA` after the fact, which a pipeline cannot do). Its errors are ignored, like those of `refresh`: a failed cleanup must not stop consuming.
- `transient` decides whether a read or claim error stops `Consume`: errors without a Redis reply (network, pool) and `LOADING`, `READONLY`, `MASTERDOWN`, `CLUSTERDOWN`, `TRYAGAIN`, `UNBLOCKED` (a failover unblocks the reads of a demoted master), `BUSY` (not `BUSYGROUP`), `MISCONF`, `NOREPLICAS` and max clients are retried after `errorWait`. Every other reply, and `redis.ErrClosed`, returns, so a deleted group stops the app rather than leaving it up without consuming.
- `XReadGroupArgs.Block` must always be set: its zero value blocks forever.

### SQL query log

- Off, `New` opens the pool with `sql.Open` and nothing wraps the driver. On, it finds the driver through a `*sql.DB` it never connects, and opens the pool with `sql.OpenDB` on a `connector` around the driver's own connector.
- The wrappers must behave exactly like the driver. database/sql changes behavior on some optional interfaces in ways a fallback cannot reproduce, so a wrapper implements those only when the driver does: `SessionResetter` and `Validator` (with both, a connection outlives a rollback after its context is canceled), `ColumnConverter` (it skips converting arguments past `NumInput`) and `RowsColumnScanner` (it replaces `Next`). Every other optional interface is always implemented, with database/sql's own fallback, which `driver_test.go` checks through database/sql on fake drivers. `connector.Driver` returns the driver, never a wrapper, so `migration.DetectDialect` keeps working. Every connection wrapper embeds `*conn`, whose `unwrap` is what `DriverConn` finds: a new variant must keep embedding it.
- `driver.ErrSkip` is never logged: the statement did not run, and database/sql prepares it instead, so it logs once, from the statement.
- A query is logged when its rows close, with the rows read, so its duration includes reading them. A context canceled before the end of the rows is the failure.
- Arguments are masked fail-closed while `SensitiveFields` is set: a placeholder the `paramPlan` cannot name is masked, and so is one with a sensitive name anywhere in its expression. A change to `params.go` keeps that property, adds its forms to `TestParamPlan`, and passes `FuzzParamPlan`.
- A logged line allocates nothing once its plan is cached (`TestRecordDoesNotAllocate`). Nothing is formatted for a line that is not written: the level is checked before any field.
- Every statement of the storages runs on a context marked by `sqllog.Quiet`, set at the entry of each exported method.

### SQL storages

- Every statement goes through `sqltx.From(ctx, db)`, and every multi-statement operation through `sqltx.Run` or `sqltx.RunWith`, so storages join the transaction of `sqltx.Transactor.Do`. The worker relies on it: `MarkCompleted` must commit or roll back with the handler.
- The exception is `sql/liveconfig`, which runs on `db` directly. forgo caches a document as soon as its save succeeds, in a cache that never expires, so a save must be committed when `Set` returns.
- Live config saves are conditional on the version and atomic: one statement per save, and zero affected rows means `forgo.ErrLiveConfigConflict`. The MySQL insert tells a duplicate key apart by reading the row afterwards, so it needs no driver error codes.
- `liveconfig` sends documents as `string`, never `[]byte`: lib/pq sends `[]byte` as `bytea`, which a `JSONB` column rejects, and MySQL refuses JSON in the binary character set.
- Each storage implements the contract and the comments in forgo's `server/worker/storage.go` exactly. The table schemas are documented in forgo's REFERENCE.md ("Storage contracts"), and `sql/internal/sqltest` creates them identically.
- Every statement reads the primary key or one of the schema's indexes, in the index's order, and stops at its limit: an `ORDER BY` that the index does not give makes the database sort every candidate row, and under MySQL's `REPEATABLE READ` also lock them all. Change a `WHERE` or `ORDER BY` only together with the indexes, in forgo's REFERENCE.md, `sql/internal/sqltest` and forgo-scaffold's migrations, and check the plan with `EXPLAIN` on both databases.
- On PostgreSQL, a statement that changes a limited batch collects the batch's keys first, `WHERE id = ANY(ARRAY(SELECT id … LIMIT $n FOR UPDATE SKIP LOCKED))` (`ctid` for tables with a composite key), never `WITH batch AS (…) UPDATE … FROM batch`. A generic plan, as pgx's statement cache can use, does not know the limit, expects many rows and joins them with a scan of the whole table (55–75 ms on a million rows, against under a millisecond).
- Claims use `FOR UPDATE SKIP LOCKED`. Status transitions only leave `InboxWaiting`. Repeating `MarkFailed` or `MarkRejected` succeeds, but `MarkCompleted` must succeed only when it moved the row itself (`unmoved` in `sql/inbox/inbox.go`): it runs in the handler's transaction, and a success for a concurrent duplicate would commit the handler's writes twice.
- Outbox claims are stamped and expired on the database clock only. `Claim` turns `ExpiredBefore` into an age (`claimAge` in `sql/outbox/outbox.go`) and compares `processing_at` with the database time minus that age, so skew between app instances and the database never shifts `ClaimTTL`. Never compare `processing_at` with a time from the app. The cleanups (`DeleteBefore`, `DeleteProcessedBefore`) turn `before` into an age the same way on MySQL.
- MySQL storages begin their own transactions at `READ COMMITTED` (`readCommitted`, through `sqltx.RunWith`), never at the session's isolation. Under `REPEATABLE READ`, InnoDB locks the gaps a locking statement reads: a claim or release blocks the application's outbox inserts (`TestIntegrationCompleteDoesNotBlockInserts`), and a locking read of a missing row before its insert deadlocks concurrent first attempts (`TestIntegrationConcurrentFirstAttempts`).
- `IncrementAttempt` counts an attempt in one upsert (`ON CONFLICT` on PostgreSQL, `ON DUPLICATE KEY UPDATE` on MySQL), never by reading the row and inserting it when missing: concurrent deliveries of a new message would then race to insert it, and all but one fail (`TestIntegrationConcurrentDuplicateAttempts`).
- MySQL storages stamp every row with `UTC_TIMESTAMP(6)`, never `CURRENT_TIMESTAMP` or a time from the app: `CURRENT_TIMESTAMP` in a `DATETIME` column follows the session time zone and its daylight saving changes, and an app time goes through the driver's `loc`.
- Each dialect lives in its own file. Placeholders differ (`$n` and `?`): keep the helpers local to the file that uses them.

### Modules

- Each client library is a module of its own, in a top-level directory named after it: `redis` (go-redis), `rabbitmq` (amqp091-go), `pubsub` (the Pub/Sub client) and `otel` (OpenTelemetry's SDK). An application then resolves only the modules of the infrastructure it uses: Go compiles only the packages an application imports, but every requirement of every module it requires sets a minimum version in its build. The root module holds the SQL adapters under `sql/`, and requires only forgo, zerolog and test-only modules.
- An adapter that needs a client library goes in the module of that library, or in a new module (see the checklist), never in the root module. Once a version is tagged, moving a package to another module breaks the builds that still have the older version in their graph, which provides the package too (`ambiguous import`).
- A module requires only forgo, never another module of this repository, not even in tests: a test-only import is a `require` in `go.mod` too, which puts that module and its requirements in the graph of every application of this one. Test helpers live in the module's own `internal/` (`sql/internal/sqltest`, `redis/internal/redistest`), and a test that needs the adapter of another module runs on a fake of the forgo contract instead (`memoryCache` in `sql/liveconfig`, `memoryStore` in `redis/liveconfigcache`).
- Packages are named after the forgo contract they implement, the same in every module (`locker`, `ratelimit`, `inbox`), unless applications usually import two of them together: the Redis live config cache is `liveconfigcache`, so that it never clashes with the SQL stores' `liveconfig`.
- `./...` stops at a module's boundary, even under a `go.work`, so every command of the [Workflow](#workflow) runs in each module.
- All modules are released together, under one version (see [Releasing](#releasing)).

### OpenTelemetry module

- Recording an operation allocates nothing once its labels were seen: every instrument's options are built once per label tuple in a `cache`, whose reads take no lock, and passed with `...`. `TestAllocations` fails otherwise. Keep it so when adding an instrument.
- Labels stay bounded: configuration names, statuses, error codes, settlement kinds, HTTP methods (`_OTHER` beyond the known ones) and status codes. Never a lock key, a message ID, a path or a name a client or producer chose.
- `observer` imports forgo's `server/http` and `server/worker` for their `State`, but not `server/grpc`, so that applications without a gRPC server do not link grpc-go's server: it compares the server name with `"grpc"` instead.
- Only `meter.Config.Global` writes OpenTelemetry's globals. Nothing else does, and `Close` does not restore them.

### Redis

- Read-modify-write logic runs as one Lua script (`redis.NewScript`) that touches a single key, so it is atomic and works on Redis Cluster.
- Time-based logic uses Redis `TIME`, never the app clock.
- The live config cache never expires its entries, and its `Set` keeps the newest version in one script, so out-of-order writes cannot regress it.
- Keys the adapter invents are namespaced (`ratelimit.KeyPrefix`, `liveconfigcache.KeyPrefix`). Keys passed in by forgo, such as lock keys, are used as given.

## Coding conventions

- Errors: prefix with the package (`sqldb:`, `redisdb:`, `rabbitmq:`, `pubsub:`, `redisstream:`, `inbox:`, `outbox:`, `liveconfig:`, `liveconfigcache:`, `locker:`, `ratelimit:`), wrap with `%w`, and declare sentinels as package-level `var`s.
- Doc comments on exported identifiers explain the contract and the why. Match the surrounding code.
- Dependencies, besides forgo: the root module `github.com/rs/zerolog` (forgo's logger, for the query log), and test-only `github.com/DATA-DOG/go-sqlmock` and the drivers `github.com/lib/pq` and `github.com/go-sql-driver/mysql` of the integration tests; `redis` `github.com/redis/go-redis/v9`, and test-only `github.com/alicebob/miniredis/v2`; `rabbitmq` `github.com/rabbitmq/amqp091-go`; `pubsub` `cloud.google.com/go/pubsub/v2`, with `google.golang.org/api/option` for its client options. A new adapter may add the client library it wraps to its module, and nothing else without a strong reason.
- Tests must not need running infrastructure. Use miniredis for Redis (it runs Lua and `TIME`, and `SetTime`/`FastForward` control the clock; stream idle times follow `SetTime`, and `SetError` fakes error replies), sqlmock for SQL (`sqlmock.NewWithDSN` plus `sql.Open("sqlmock", dsn)` exercises `sqldb.New`; storage tests set `SetMaxOpenConns(1)`, so a statement that bypasses an open transaction blocks and fails on the test's deadline), fakes of narrow interfaces for AMQP (`declarer`, `consumeChannel`, `publishChannel`, `confirmation` and `amqp.Acknowledger`), and `pstest` for Pub/Sub, the in-memory server of the client module, which the real client connects to with `option.WithGRPCConn`. Table-driven where possible, passing under `-race`.
- Integration tests (`TestIntegration…`) run the SQL storages against PostgreSQL and MySQL, the RabbitMQ broker against RabbitMQ, and the Redis Streams broker, the locker, the rate limiter and the live config cache against every Redis server in the comma-separated `ADAPTER_TEST_REDIS_ADDRS` (CI: Redis 8 and 6.2, the oldest the Redis Streams broker supports), when `ADAPTER_TEST_POSTGRES_DSN`, `ADAPTER_TEST_MYSQL_DSN`, `ADAPTER_TEST_RABBITMQ_URL` and `ADAPTER_TEST_REDIS_ADDRS` are set, and skip otherwise. CI sets them for its service containers. The Redis tests run through `redis/internal/redistest`, which empties the database it opens: go test runs packages in parallel, so every package has a database of its own on each server. The SQL tests of a package reset only its own tables on the database of the DSN, and a test that uses the tables of other packages, such as `TestIntegrationForgotest` with the outbox's and the inbox's, opens a database of its own with `sqltest.OpenDatabase`. MySQL runs them in a session time zone behind UTC, so a timestamp that follows the session fails them. They check what sqlmock, miniredis and the fakes cannot: that the SQL runs, the documented schema, the brokers' own behavior, and the Lua scripts in Redis's own Lua. The RabbitMQ recovery tests open the broker with `Config.open`, dialing through a `faultyNetwork` that cuts the connections as a lost network would, refuses new ones, or hangs up on them as a load balancer does while the broker behind it is down, or slows the reads of the publishing connection, so that publishes in flight wait together, and force a channel loss with an acknowledgement of an unknown delivery tag, so they need no management plugin. A fault that takes a whole Redis server (a long script, `CONFIG SET`, `REPLICAOF`) would fail the tests of the packages running at the same time, so the Redis Streams tests unblock one read with `CLIENT UNBLOCK … ERROR` live and fake the other error replies on miniredis.
- miniredis differs from Redis in ways the Redis Streams unit tests work around: it counts `XCLAIM … JUSTID` as a delivery, reports `0` instead of `0-0` as a group position, trims `MAXLEN ~` exactly, updates a consumer's idle time only on claims (`seen` in the tests claims an entry that is not pending, which also creates the consumer), and keeps its blocking commands canceled after `Restart` (`TestConsumeErrors/restart`). `TestIntegrationBroker` checks the delivery counts, the trimming and the idle times on Redis. Pointed at miniredis, it fails on the delivery counts and the sweep.

## Workflow

Run these in every module a change touches (`.`, `redis`, `rabbitmq`, `pubsub`, `otel`):

```sh
go build ./...
go vet ./...
go test -race ./...
gofmt -l .        # must print nothing
go run honnef.co/go/tools/cmd/staticcheck@v0.8.2 ./...
```

CI (`.github/workflows/ci.yml`) runs these on every push and pull request, in a job per module with the service containers of its integration tests (PostgreSQL and MySQL for the root module, Redis 8 and 6.2 for `redis`, RabbitMQ for `rabbitmq`), plus `go mod tidy -diff`, govulncheck and `go test` without the race detector. A service whose image is empty in the job's matrix row is not started. Each module builds against the forgo version its `go.mod` requires, so a change that needs an unreleased forgo change passes once its `go.mod` requires the forgo commit that holds it.

When you change behavior:

1. Update [REFERENCE.md](REFERENCE.md) in the same change whenever a config field, default, constructor, wire format or error changes. Update [README.md](README.md) only if the pitch, the table or the headline example is affected.
2. If an adapter is added or renamed, update the Adapters section of forgo's REFERENCE.md and the adapter row of its README.md.
3. If you fix an item from [Known gaps](#known-gaps), remove it. If you find a new one, add it.
4. Doc comments render on pkg.go.dev, with the `Example` functions of `example_test.go` files. Keep the examples in line with REFERENCE.md.

### Releasing

Versions follow semantic versioning. `go get` picks the latest tag, and pkg.go.dev documents it.

Every module is released at each release, under the same version, so that applications have one rule to follow: the same version of every module. A forgo contract change usually touches several modules anyway.

1. In every module, require the same released forgo (`go get github.com/efegreat/forgo@v1.2.3`), never a commit of its `main`, so that applications of the release get a forgo that pkg.go.dev documents. The release job of CI refuses the tag of a module that replaces forgo.
2. Check that CI passes on `main`.
3. Tag the commit once per module, the nested modules with their directory as a prefix, and push each tag on its own: GitHub starts no workflow for a push of more than three tags, so pushing them together releases nothing. The loop lists the tags itself, since zsh does not split a variable into words:

   ```sh
   v=v1.2.3
   for t in $v otel/$v pubsub/$v rabbitmq/$v redis/$v; do
     git tag "$t" && git push origin "$t"
   done
   ```

   CI runs on each tag, then creates its GitHub release with generated notes and asks the module proxy for the version, such as `github.com/efegreat/forgo-adapter/redis@v1.2.3`, so that pkg.go.dev lists it. A release that exists already, such as one published on GitHub, is kept with its notes. A tag whose push started no workflow is released by running CI on it: `gh workflow run ci.yml --ref redis/v1.2.3`. Do not ask the proxy for a version before its tag exists: it remembers the miss for up to half an hour, and the release job's request then fails.

### Checklists

**New resource**
- [ ] `Config` value type, `Sanitize()` that never mutates shared slices or maps, `New() (forgo.Resource, error)`.
- [ ] Validation before connecting. Verification (ping, declare) in `New`. Cleanup on every failure path.
- [ ] `Value()` type documented, and tests for `Sanitize`, a successful `New` and a failing one.
- [ ] REFERENCE.md section with a config table (field, default, description), plus rows in the overview table and README.

**New provider**
- [ ] `NewX(dep) *X` with the narrowest dependency type.
- [ ] Compile-time interface assertion in tests, and tests against miniredis or sqlmock.
- [ ] Atomic under concurrent instances (single script or `SKIP LOCKED`).
- [ ] REFERENCE.md section, plus rows in the overview table and README.

**New module**
- [ ] Only for a client library that no module wraps yet. A top-level directory named after it, with a `go.mod` (`module github.com/efegreat/forgo-adapter/<dir>`) that requires the forgo version the other modules require and the library, and no other module of this repository.
- [ ] A row in the CI matrix with the services of its integration tests, its directory in Dependabot's `directories`, its tag in the release loop of [Releasing](#releasing), and in the module lists of AGENTS.md, CONTRIBUTING.md, README.md and REFERENCE.md's Installation.

**New broker**
- [ ] Resource whose `Value()` is `worker.IBroker`, with named publishers and subscribers matching worker config names.
- [ ] Identity headers written on publish and read back through `worker.NewMessageFromDelivery`.
- [ ] `Complete`/`Retry`/`Reject` semantics as in forgo's broker contracts, and `Consume` that joins its handlers.
- [ ] What the subscriber holds per handler (a prefetch, a buffer, a pool) sized in `NewSubscriber` by `worker.SubscriberOptions.Concurrency`, and deliveries only while `Consume` runs.
- [ ] A dead-letter option if the broker supports one.
- [ ] `Consume` returns only errors that do not pass on their own, because the worker stops on any error it returns. List what the broker answers during a failover, an overload, a quota, a memory limit and a restart, and receive again after a pause through those (`redisstream`'s `transient`, `pubsub`'s `retryable`).
- [ ] An acknowledgement handle that belongs to a connection or a channel never reaches its successor: a delivery buffered from a lost channel must not settle a message of the reopened one (`rabbitmq`'s `ackGuard` and the generation of each `stream`).
- [ ] A dead-letter copy that fails never acknowledges its message, which waits the longest retry delay before it comes back (`rabbitmq`'s `deadLetter.park`, `redisstream`'s `longestDelay`): a destination that keeps refusing copies would otherwise loop and take every handler. The subscriber's copies wait for a recovery in progress, while the outbox's publishers fail fast, so the relay moves on.
- [ ] Every wait on the broker in `Consume` and `Close` is bounded (`rabbitmq`'s `closeWithin`, `pubsub`'s `flushWait` and `stopWait`), so that SIGTERM during an outage stops within Kubernetes' 30 seconds, forgo's relay included.
- [ ] A consumer that the broker ends, for a deleted queue, a consumer timeout, a lost lease or a rebalance, is subscribed again, or `Consume` returns an error: never a subscriber that receives nothing (`rabbitmq`'s `consumeAgain`).
- [ ] `New` starts against a broker that refuses writes when the topology already exists (`redisstream`'s `hasGroup` under OOM), so a restarted replica does not fail its bootstrap.
- [ ] Publishers do not share a connection with subscribers on a broker that throttles a publishing connection (`rabbitmq`'s `publishConn`).
- [ ] A subscriber's work per poll does not grow with its backlog of pending or retried messages (`redisstream`'s `claim`).
- [ ] REFERENCE.md says that a dead letter can be stored more than once, what `Message.Key` means on the broker, and how long a handler may run before the broker delivers its message again.
- [ ] Tests for each item above, on the broker wherever they can run there. Before the broker ships, live tests on a copy of forgo-scaffold: faults that take the whole server (lost and refused connections, a hung broker, a restart, SIGTERM and SIGKILL of a replica), then a long run under them. The live tests of the three brokers found every item above in at least one of them. Prove a suspected broker or emulator bug with the official client alone before changing the adapter for it.

## Known gaps

When you find one, verify it against the code and add it here with a `file:line` reference. Delete it in the change that fixes it.

- With the query log on, the function given to `sql.Conn.Raw` receives the log's connection, and only code that calls `DriverConn` reaches the driver's (`sql/sqldb/driver.go:92`). A library that calls `Raw` itself and asserts the driver's type, such as pgx's `*stdlib.Conn`, fails: database/sql has no convention for unwrapping a connection.
- The Pub/Sub adapter is tested against `pstest` only, which applies neither retry-policy delays nor IAM.
